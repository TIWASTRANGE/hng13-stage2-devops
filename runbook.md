# Operational Runbook - Blue/Green Deployment Alerts

## Overview

This runbook describes alerts generated by the Blue/Green deployment monitoring system and provides operator response procedures.

---

## Alert Types

### 1. Failover Detected

**Message Format:**
```
Failover Detected!
- From: blue
- To: green
- Time: 2025-10-25 15:30:00
- Action: Check health of blue container
```

**What It Means:**
- Nginx has automatically switched traffic from one pool to another
- The primary pool likely failed or became unresponsive
- This is expected behavior during failures or chaos testing

**Operator Actions:**

1. **Verify the cause:**
```bash
   # Check which container is unhealthy
   docker compose ps
   
   # Check logs of the failed pool
   docker compose logs app_blue  # or app_green
```

2. **Determine if intentional:**
   - Was chaos testing being performed?
   - Was there a planned maintenance?
   - Check recent deployments

3. **If unintentional failure:**
```bash
   # Investigate application logs
   docker compose logs app_blue --tail=100
   
   # Check for resource issues
   docker stats
   
   # Restart failed container if needed
   docker compose restart app_blue
```

4. **Monitor recovery:**
```bash
   # Watch for traffic to return to primary
   docker compose logs -f alert_watcher
   
   # Test endpoints directly
   curl http://localhost:8081/healthz
   curl http://localhost:8080/version
```

5. **Document the incident:**
   - Record time, cause, and resolution
   - Update monitoring thresholds if needed

**Auto-Recovery:**
- Nginx will automatically retry the failed pool after `fail_timeout` (10s)
- No manual intervention needed if container recovers
- Traffic returns to primary automatically

### 2. High Error Rate Detected

**Message Format:**
```
High Error Rate Detected!
- Error Rate: 5.50% (threshold: 2%)
- Errors: 11/200 requests
- Window: Last 200 requests
- Time: 2025-10-25 15:35:00
- Action: Inspect upstream logs and consider manual pool toggle
```

**What It Means:**
- The active pool is returning HTTP 5xx errors above the configured threshold
- Could indicate application bugs, resource exhaustion, or dependency failures
- System may be partially degraded

**Operator Actions:**

1. **Immediate assessment:**
```bash
   # Check current error rate
   docker compose logs nginx | tail -50 | grep "upstream_status=5"
   
   # Identify which pool is active
   curl -i http://localhost:8080/version | grep X-App-Pool
```

2. **Investigate application issues:**
```bash
   # Check application logs
   docker compose logs app_blue --tail=100
   docker compose logs app_green --tail=100
   
   # Look for errors, exceptions, or warnings
   docker compose logs app_blue | grep -i error
```

3. **Check resource constraints:**
```bash
   # CPU and memory usage
   docker stats --no-stream
   
   # Disk space
   df -h
   
   # Network connectivity
   docker compose exec app_blue ping -c 3 google.com
```

4. **If errors persist - Manual failover:**
```bash
   # Edit .env to switch active pool
   nano .env
   # Change: ACTIVE_POOL=green
   
   # Restart Nginx to apply
   docker compose restart nginx
   
   # Verify switch
   curl -i http://localhost:8080/version
```

5. **Root cause analysis:**
   - Check external dependencies (databases, APIs)
   - Review recent code changes
   - Examine application metrics
   - Check for timeouts or connection issues

6. **If both pools are failing:**
```bash
   # This indicates a systemic issue
   # Check infrastructure:
   docker compose down
   docker compose up -d
   
   # Or investigate external dependencies
```

**Prevention:**
- Set appropriate timeout values
- Implement circuit breakers in application
- Monitor dependencies
- Regular health checks

### 3. Recovery Detected (Future Enhancement)

**Message Format:**
```
Recovery Detected
- Pool: blue
- Status: Healthy
- Traffic: Restored
- Time: 2025-10-25 15:40:00
```

**What It Means:**
- Previously failed pool has recovered
- Traffic has been restored to the primary pool
- System is operating normally

**Operator Actions:**
- Verify both pools are healthy
- Review what caused the initial failure
- Update documentation or monitoring if needed

## Maintenance Mode

### When to Enable

Enable maintenance mode to suppress alerts during:
- Planned deployments
- Manual chaos testing
- Infrastructure maintenance
- Load testing

### How to Enable
```bash
# Edit .env
nano .env

# Set maintenance mode
MAINTENANCE_MODE=true

# Restart watcher
docker compose restart alert_watcher
```

### How to Disable
```bash
# Edit .env
nano .env

# Disable maintenance mode
MAINTENANCE_MODE=false

# Restart watcher
docker compose restart alert_watcher
```

**Important:** Always disable maintenance mode after completing planned work!

## Configuration Parameters

### Error Rate Threshold

**Parameter:** `ERROR_RATE_THRESHOLD`  
**Default:** 2 (%)  
**Description:** Percentage of 5xx errors that triggers an alert

**Tuning:**
- Increase for less sensitive alerting (fewer false positives)
- Decrease for more sensitive alerting (catch issues earlier)
- Consider your application's normal error rate
```bash
# Example: Increase threshold to 5%
ERROR_RATE_THRESHOLD=5
```

### Window Size

**Parameter:** `WINDOW_SIZE`  
**Default:** 200 requests  
**Description:** Number of recent requests to analyze for error rate

**Tuning:**
- Larger window = more stable, slower to detect issues
- Smaller window = faster detection, more volatile
- Balance based on traffic volume
```bash
# Example: Larger window for high-traffic apps
WINDOW_SIZE=300
```

### Alert Cooldown

**Parameter:** `ALERT_COOLDOWN_SEC`  
**Default:** 300 seconds (5 minutes)  
**Description:** Minimum time between duplicate alerts

**Tuning:**
- Increase to reduce alert noise
- Decrease for more frequent updates during incidents
- Consider your team's response time
```bash
# Example: Shorter cooldown for critical systems
ALERT_COOLDOWN_SEC=120
```

## Troubleshooting

### No Alerts Received

**Possible Causes:**
1. Slack webhook URL not configured
2. Watcher container not running
3. No traffic to trigger alerts
4. Maintenance mode enabled

**Steps:**
```bash
# Check watcher is running
docker compose ps alert_watcher

# Check watcher logs
docker compose logs alert_watcher

# Verify Slack webhook
echo $SLACK_WEBHOOK_URL

# Test Slack webhook manually
curl -X POST -H 'Content-type: application/json' \
  --data '{"text":"Test message"}' \
  $SLACK_WEBHOOK_URL

# Disable maintenance mode
nano .env  # Set MAINTENANCE_MODE=false
docker compose restart alert_watcher
```

### Too Many Alerts

**Possible Causes:**
1. Threshold too low
2. Cooldown too short
3. Application actually having issues

**Steps:**
```bash
# Increase threshold
nano .env  # Increase ERROR_RATE_THRESHOLD

# Increase cooldown
nano .env  # Increase ALERT_COOLDOWN_SEC

# Enable maintenance mode temporarily
nano .env  # Set MAINTENANCE_MODE=true

# Restart watcher
docker compose restart alert_watcher
```

### Alerts Not Accurate

**Possible Causes:**
1. Log parsing issues
2. Window size too small
3. Timing issues

**Steps:**
```bash
# Check log format
docker compose exec nginx cat /var/log/nginx/access.log | tail -5

# Verify watcher is parsing correctly
docker compose logs alert_watcher | grep "pool="

# Increase window size for more stable metrics
nano .env  # Increase WINDOW_SIZE
docker compose restart alert_watcher
```

## Testing Alerts

### Test Failover Alert
```bash
# Trigger chaos on Blue
curl -X POST "http://localhost:8081/chaos/start?mode=error"

# Generate traffic to trigger failover
for i in {1..10}; do
  curl http://localhost:8080/version
  sleep 0.5
done

# Check Slack for failover alert
# Check watcher logs
docker compose logs alert_watcher
```

### Test Error Rate Alert
```bash
# Trigger chaos to generate 5xx errors
curl -X POST "http://localhost:8081/chaos/start?mode=error"

# Generate enough requests to exceed threshold
# With ERROR_RATE_THRESHOLD=2 and WINDOW_SIZE=200
# Need ~5+ errors in 200 requests
for i in {1..250}; do
  curl -s http://localhost:8080/version > /dev/null
  sleep 0.1
done

# Check Slack for error rate alert
# Check watcher logs
docker compose logs alert_watcher

# Stop chaos
curl -X POST "http://localhost:8081/chaos/stop"
```

## Emergency Procedures

### Complete System Failure
```bash
# Stop everything
docker compose down

# Clean up
docker system prune -f

# Restart from scratch
docker compose up -d

# Monitor startup
docker compose logs -f
```

### Split Brain (Both Pools Failing)
```bash
# Check external dependencies first
# Database, APIs, network, etc.

# If infrastructure issue:
docker compose restart

# If application issue:
# Roll back to last known good version
nano .env  # Update image tags
docker compose pull
docker compose up -d
```

### Stuck in Failover Loop
```bash
# Indicates both pools are unhealthy
# Stop automated failover
docker compose stop nginx

# Fix underlying issue
docker compose logs app_blue
docker compose logs app_green

# Restart once fixed
docker compose start nginx
```

## Monitoring Commands

### Quick Status Check
```bash
# All containers
docker compose ps

# Recent alerts
docker compose logs alert_watcher --tail=20

# Current active pool
curl -s http://localhost:8080/version | grep X-App-Pool

# Health status
curl http://localhost:8081/healthz  # Blue
curl http://localhost:8082/healthz  # Green
```

### Detailed Investigation
```bash
# Nginx access logs (last 50)
docker compose exec nginx tail -50 /var/log/nginx/access.log

# Error count in last 100 requests
docker compose exec nginx tail -100 /var/log/nginx/access.log | \
  grep -c "upstream_status=5"

# Pool distribution
docker compose exec nginx tail -200 /var/log/nginx/access.log | \
  grep -o "pool=[a-z]*" | sort | uniq -c

# Response times
docker compose exec nginx tail -100 /var/log/nginx/access.log | \
  grep -o "request_time=[0-9.]*" | \
  awk -F= '{sum+=$2; count++} END {print "Avg:", sum/count, "s"}'
```

## Appendix: Log Format Reference

### Nginx Log Fields
```
pool=blue                          # Which pool served the request
release=blue-v1.0.0               # Release identifier
upstream_status=200               # HTTP status from upstream
upstream_addr=172.18.0.2:3000    # Upstream server address
request_time=0.045                # Total request time (seconds)
upstream_response_time=0.042      # Upstream response time (seconds)
```

### Sample Log Line
```
172.18.0.1 - - [25/Oct/2025:15:30:45 +0000] "GET /version HTTP/1.1" 200 57 
"-" "curl/7.81.0" pool=blue release=blue-v1.0.0 upstream_status=200 
upstream_addr=172.18.0.2:3000 request_time=0.045 upstream_response_time=0.042
```
